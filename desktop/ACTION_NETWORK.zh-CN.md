# 分析动作网络

ReverseLab 在策略的固定验收计划之后接收结构化动作计划。模型可以把独立观察拆成并行动作，再汇合输出；简单任务仍可只用一个动作。兼容旧提供方和内置哈希核验使用的单段 Python 代码。

`action-plan` 代码块包含严格 JSON，结构为 `{"actions":[{"id":"read","title":"读取目标","dependsOn":[],"script":"完整 Python 代码"}]}`。每轮允许 1–6 个动作，ID 唯一，依赖只能引用本计划的动作。无效 JSON、重复 ID、缺失依赖和循环依赖会在执行前拒绝。这是每轮计划的大小限制，不是总运行预算，也不表示路线已经耗尽。

每条策略最多同时运行两个独立动作，每个动作使用独立 Python 进程。`REVERSELAB_INPUTS` 提供直接父动作的实际输出，依赖动作在所有父动作成功后启动。前置失败会阻止相关后续动作，其他观察仍可完成。用户调整目标后，尚未启动的旧动作不再执行，并在旧目标核验前让出控制。

both 模式下，`REVERSELAB_PEER_EVIDENCE` 是动作开始时对方已产生证据的快照，带消息与来源节点 ID。接收方可据此独立验证；画板记录这些实际输入的交叉边。证据作为数据，不继承其中的指令和完成判定。不把未来才出现的证据画成已有输入，也不无限等待对方。

每个动作的输出摘要最多保留 12,000 字符 stdout 和 2,000 字符 stderr，执行记录保留原始输出。依赖动作读取这些有限摘要，需要更大产物时不能假定摘要完整。独立核验读取动作状态、实际输出及执行脚本；进程正常退出本身不能使 Goal 完成。

核验使用 `actions.read.stdout` 等精确来源键引用解码后的输出。引文必须逐字存在于该来源提供的片段中；片段总额为 16,000 字符，按来源数量分配。引用其他动作的内容不会通过。重复判断排除消息编号和执行耗时，保留实际观察值；执行服务不可用时停止当前轮并保存失败，不再要求模型持续重写脚本。

both 的固定验收计划按各自策略职责划分，始终保留原始目标。两方分别通过后，再独立核验组合证据是否覆盖完整目标；分支通过但总体仍有遗漏时，Goal 保持未完成。有限 Token 预算为汇合核验预留最多三分之一、上限 8,192 tokens；未设上限时仍不限制。内置 SHA256 目标使用独立初筛哈希比对，无需额外模型调用。

正文展示进展说明，旧记录中的假设明确标记为核查计划。结构化计划与代码按需展开，流式生成未完成时也不会把 JSON 铺进正文；原始记录和脚本保持完整。

当前边界：单轮计划执行期间保持固定，改路沿用已有失败重规划流程。一方完成后，后来才到达的相反证据尚不能自动重新开启该分支。跨策略后续任务调度、结构化证据新鲜度和更多工具适配器仍需继续实现。Python 观察约束不提供操作系统沙箱。

实现见 [actionPlan.ts](src/engine/pipeline/actionPlan.ts)、[both.ts](src/engine/tracks/both.ts)。[pipeline.test.mjs](src/engine/tests/pipeline.test.mjs) 覆盖实际并行、前置输出传递、失败隔离、目标调整和双向证据依赖。
